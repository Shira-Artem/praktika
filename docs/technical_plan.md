# Технический план реализации проекта (v2, senior-ревизия)

## Тема проекта

**Разработка масштабируемой, контейнеризированной системы сбора, обработки и хранения событий игровой аналитики с применением СУБД ClickHouse и языка программирования Python.**

## Главный фокус проекта

Главная цель проекта — разработать **backend-систему для событийной игровой аналитики**.

Аналитика, метрики и дашборды в этом проекте являются не основной целью, а демонстрационным слоем. Они нужны для подтверждения того, что backend корректно:

- принимает события;
- валидирует данные;
- передаёт события через очередь сообщений;
- обрабатывает поток событий;
- сохраняет данные в ClickHouse;
- позволяет получать агрегированные результаты по сохранённым событиям.

Иными словами, основной объект разработки — не аналитическая BI-система, а универсальный backend-pipeline для работы с игровыми событиями.

## 0. Ключевые архитектурные решения (READ FIRST)

Этот раздел добавлен в v2. Здесь зафиксированы решения, которые влияют на всю систему и должны быть приняты **до** написания кода. Всё остальное в плане подчиняется этим решениям.

### 0.1. Гарантия доставки: at-least-once

Система гарантирует **at-least-once** доставку. Это значит:

- ни одно событие не теряется при штатной работе и при перезапусках;
- **дубли возможны и являются нормой**, а не редким исключением. Любой ретрай после записи в ClickHouse, но до коммита offset, приведёт к повторной записи батча.

Полная exactly-once семантика в MVP **не реализуется** и честно выносится в расширения. Защита от дублей строится на уровне запросов и/или `ReplacingMergeTree` (см. 0.4).

### 0.2. Семантика ответа `202 Accepted`

`202 Accepted` означает: **событие принято брокером сообщений** (получен ack от Redpanda), но ещё не обязательно записано в ClickHouse.

- Продюсер настроен на `acks=all`.
- API возвращает `202` **только после** подтверждения записи в топик.
- Если брокер недоступен и подтверждение не получено — API возвращает **`503 Service Unavailable`**, а не `202`. Клиент не должен считать событие принятым, если брокер его не подтвердил.

Это осознанный размен: чуть выше латентность на запись, зато `202` не врёт.

### 0.3. `event_id` — идемпотентный ключ на клиенте

- `event_id` **желательно генерировать на стороне клиента/генератора** (формат ULID) и использовать как идемпотентный ключ.
- Если клиент не передал `event_id`, `Event API` генерирует его сам. **Важно:** в этом случае ретрай одного и того же HTTP-запроса создаст два разных `event_id`, и дедупликация по нему станет невозможной. Поэтому для нагрузочного генератора `event_id` генерируется на стороне генератора.

Почему ULID, а не UUID4: ULID сортируется по времени, читаем и лучше ложится в аналитические запросы и в `ORDER BY`.

### 0.4. Модель дедупликации

Так как система at-least-once, дубли обрабатываются на уровне хранения/чтения:

- В MVP: дубли допускаются, метрики считаются приблизительными. Это честно проговаривается на защите.
- Расширение: таблица переводится на `ReplacingMergeTree` с ключом дедупликации по `event_id`.
- **Критично помнить:** `ReplacingMergeTree` схлопывает дубли **отложенно, только при мерже партиций**. Поэтому корректный подсчёт требует либо `SELECT ... FINAL`, либо дедупликации в самом запросе (`argMax` / `GROUP BY event_id`). Просто наличие `ReplacingMergeTree` не гарантирует отсутствие дублей в моменте.

### 0.5. `event_time` — это untrusted-поле

`event_time` приходит от клиента и не может быть доверенным для критичных операций (в частности, для партиционирования).

Правило валидации в `Event API`:

- если `event_time` в будущем более чем на `MAX_FUTURE_SKEW` (например, 5 минут) — либо reject, либо clamp к `received_at`;
- если `event_time` старше `MAX_PAST_AGE` (например, 90 дней) — reject или пометка;
- партиционирование в ClickHouse завязано на валидированное время, чтобы кривой клиент не создал мусорные партиции вроде `209912`.

## 1. Общее описание системы

Проект представляет собой универсальную backend-систему для сбора, обработки и хранения событий игровой аналитики.

Система должна уметь принимать события из разных источников:

- игровой клиент;
- тестовый массив данных от преподавателя;
- локальный генератор событий;
- ручные запросы через Swagger, Postman или curl.

Система не должна быть жёстко привязана к одной конкретной игре. Поэтому структура события должна содержать универсальные поля, а специфичные игровые параметры должны храниться в отдельном поле `properties`.

Пример универсального события:

```json
{
  "event_type": "level_completed",
  "event_time": "2026-07-16T12:30:00Z",
  "game_id": "arena_escape",
  "player_id": "player_123",
  "session_id": "session_456",
  "platform": "android",
  "app_version": "1.0.0",
  "country": "RU",
  "properties": {
    "level_id": 4,
    "duration_seconds": 128,
    "difficulty": "normal"
  }
}
```

Такой подход позволяет использовать backend для разных игр и разных типов событий без постоянного изменения схемы базы данных.

## 2. Архитектура backend-компонентов

Общая архитектура системы:

```text
Игровой клиент / тестовый массив / генератор событий
        ↓
Event API на FastAPI  (acks=all → 202 только после ack брокера)
        ↓
Очередь сообщений Redpanda/Kafka  (topic game-events, 6–12 партиций)
        ↓
Event Processor на Python  (consumer group, ручной commit offset)
        ↓
ClickHouse  (батч-вставка, MergeTree)
        ↓
Analytics API / Grafana / SQL-запросы
```

Смысл такой архитектуры:

- API быстро принимает события и не ждёт долгой записи в базу;
- очередь сообщений защищает систему от всплесков нагрузки;
- обработчик событий можно масштабировать независимо от API (за счёт нескольких партиций топика);
- ClickHouse эффективно хранит большой объём событий;
- аналитический слой показывает, что данные действительно сохранены и доступны для запросов.

## 3. Роли каждого сервиса

### 3.1. Event API

`Event API` — основной входной сервис системы.

Технологии:

- Python 3.12+;
- FastAPI;
- Pydantic v2 (+ `pydantic-settings`);
- Kafka-compatible producer — рекомендуется `aiokafka` (нативно ложится на async FastAPI) либо `confluent-kafka`.

Задачи сервиса:

- принимать одиночные события;
- принимать пачки событий;
- валидировать базовую структуру события (Pydantic-модель);
- валидировать `event_time` (см. 0.5);
- ограничивать размер `properties` (например, ≤ 16 КБ) и общий размер запроса;
- генерировать `event_id` (ULID), если клиент его не передал;
- добавлять служебное поле `received_at`;
- отправлять событие в очередь сообщений с `acks=all`;
- возвращать клиенту ответ: `202` при ack брокера, `503` при недоступности брокера, `422` при ошибке валидации.

Важно: `Event API` не должен выполнять сложную аналитику и не должен напрямую зависеть от скорости записи в ClickHouse. Его задача — принять событие, провалидировать и безопасно передать дальше. Ключ сообщения в топике — `player_id` (см. раздел 8).

### 3.2. Event Processor

`Event Processor` — фоновый сервис обработки событий.

Технологии:

- Python 3.12+;
- Kafka-compatible consumer — рекомендуется `confluent-kafka` (обёртка над librdkafka, надёжный контроль offset);
- ClickHouse client — рекомендуется `clickhouse-connect` (официальный, удобная батч-вставка);
- Pydantic v2.

Задачи сервиса:

- читать события из очереди сообщений;
- десериализовать JSON;
- повторно валидировать структуру события;
- группировать события в батчи;
- записывать батчи в ClickHouse;
- **коммитить offset только после успешной записи батча** (`enable.auto.commit = false`);
- обрабатывать `SIGTERM` (graceful shutdown, см. раздел 9);
- ретраить запись в ClickHouse с экспоненциальным backoff;
- структурированно (JSON) логировать ошибки обработки;
- не терять события при временной недоступности ClickHouse.

Этот сервис является ключевым элементом backend-pipeline, потому что именно он связывает очередь сообщений и аналитическое хранилище.

### 3.3. ClickHouse

`ClickHouse` — основное хранилище событий.

Задачи:

- хранить большой поток игровых событий;
- обеспечивать быстрые аналитические запросы;
- позволять фильтровать данные по времени, игре, типу события, игроку и сессии;
- хранить универсальные события с дополнительными параметрами в `properties`;
- ускорять частые запросы через `MATERIALIZED`-колонки, не теряя универсальность схемы (см. раздел 7).

ClickHouse выбран потому, что он хорошо подходит для аналитических нагрузок, больших объёмов событий и быстрых агрегирующих запросов.

### 3.4. Redpanda или Kafka

Очередь сообщений нужна для отделения приёма событий от их записи в базу.

Для учебного проекта рекомендуется использовать **Redpanda**, потому что она совместима с Kafka API, но проще запускается в Docker Compose.

Задачи очереди:

- принимать события от `Event API`;
- временно хранить события до обработки;
- сглаживать пики нагрузки;
- позволять запускать несколько обработчиков событий параллельно;
- повышать отказоустойчивость системы.

**Важно:** топик `game-events` должен иметь **несколько партиций (6–12)**, иначе масштабирование `Event Processor` не даст эффекта — в одной consumer group одна партиция обслуживается ровно одним консьюмером.

### 3.5. Event Generator / Importer

`Event Generator` — тестовый источник данных.

Задачи:

- генерировать тестовые события (с `event_id` на своей стороне, см. 0.3);
- имитировать действия игроков (игроки, сессии, последовательности событий);
- отправлять события в `Event API` (одиночно и батчами);
- создавать нагрузку для проверки backend-pipeline.

Дополнительно можно сделать режим импорта событий из файла, если преподаватель даст тестовый массив данных в JSON или CSV.

### 3.6. Analytics API

`Analytics API` — минимальный демонстрационный слой поверх ClickHouse.

Задачи:

- выполнять простые запросы к ClickHouse;
- возвращать агрегированные данные в JSON;
- демонстрировать, что события корректно сохранены;
- показывать базовые метрики по событиям.

Этот сервис не является главным компонентом проекта. Он нужен для проверки и демонстрации работы backend-системы. Бизнес-эндпоинты живут под префиксом `/analytics/...` (см. примечание про неймспейс `/metrics` в разделе 6).

### 3.7. Grafana

`Grafana` — опциональный компонент.

Её можно добавить после MVP, если потребуется визуальная демонстрация данных.

В рамках MVP Grafana не обязательна. Вместо неё достаточно `Analytics API` и SQL-запросов к ClickHouse.

## 4. Контейнеры Docker Compose

Минимальный состав контейнеров:

```text
event-api          — FastAPI-сервис приёма событий
event-processor    — Python-сервис обработки очереди
redpanda           — Kafka-compatible очередь сообщений
clickhouse         — аналитическая СУБД
event-generator    — генератор тестовых игровых событий
```

Дополнительные контейнеры после MVP:

```text
analytics-api      — API для простых аналитических запросов
grafana            — визуализация метрик
```

Рекомендуемый состав MVP:

```text
event-api
event-processor
redpanda
clickhouse
event-generator
```

### 4.1. Обязательные требования к compose (v2)

Без этих пунктов compose будет флапать при первом запуске:

- **Healthcheck'и** для `clickhouse` и `redpanda`.
- Зависимости через `depends_on: { condition: service_healthy }` — `event-processor` и `event-api` стартуют только после готовности брокера и БД. Иначе processor уходит в рестарт-луп.
- `restart: unless-stopped` для сервисов.
- Явный маунт init-SQL в `docker-entrypoint-initdb.d` контейнера ClickHouse (директория `db/clickhouse/init/`).
- Все параметры (адреса брокера, ClickHouse, размеры батча) — через переменные окружения из `.env` (см. `.env.example`).

## 5. Формат универсального игрового события

Базовая модель события:

```json
{
  "event_id": "01HXYZ...ULID",
  "event_type": "level_completed",
  "event_time": "2026-07-16T12:30:00Z",
  "game_id": "arena_escape",
  "player_id": "player_123",
  "session_id": "session_456",
  "platform": "android",
  "app_version": "1.0.0",
  "country": "RU",
  "properties": {
    "level_id": 4,
    "duration_seconds": 128,
    "result": "success"
  }
}
```

### Обязательные поля

```text
event_type
event_time
game_id
player_id
session_id
```

### Необязательные поля

```text
event_id
platform
app_version
country
properties
```

Если `event_id` не передан клиентом, его может сгенерировать `Event API` (с оговоркой из 0.3).

### Назначение поля properties

Поле `properties` нужно для хранения игровых параметров, которые зависят от конкретной игры или конкретного типа события.

Пример для события `level_started`:

```json
{
  "level_id": 3,
  "difficulty": "hard"
}
```

Пример для события `purchase_made`:

```json
{
  "item_id": "sword_01",
  "price": 199,
  "currency": "coins"
}
```

Пример для события `player_died`:

```json
{
  "level_id": 5,
  "cause": "enemy",
  "enemy_type": "boss"
}
```

Такой формат делает backend универсальным и не привязывает его к одной конкретной игре.

### Единый контракт события (v2)

Pydantic-модель события **не дублируется** между `event-api` и `event-processor`. Она выносится в общий пакет `shared/` (или отдельный локально устанавливаемый пакет) как единственный источник правды для контракта. Оба сервиса импортируют одну и ту же модель.

## 6. API-контракты

> **Примечание по неймспейсу (v2):** путь `/metrics` зарезервирован под Prometheus-метрики сервисов. Поэтому бизнес-аналитика вынесена под префикс `/analytics/...`, чтобы не было коллизии с системным мониторингом.

### 6.1. GET /health

Назначение: проверка доступности сервиса.

Пример ответа:

```json
{
  "status": "ok",
  "service": "event-api"
}
```

Расширенный вариант:

```json
{
  "status": "ok",
  "dependencies": {
    "redpanda": "ok"
  }
}
```

### 6.2. POST /events

Назначение: приём одного события.

Пример запроса:

```json
{
  "event_type": "session_started",
  "event_time": "2026-07-16T12:30:00Z",
  "game_id": "arena_escape",
  "player_id": "player_123",
  "session_id": "session_456",
  "platform": "android",
  "app_version": "1.0.0",
  "country": "RU",
  "properties": {}
}
```

Пример успешного ответа:

```json
{
  "status": "accepted",
  "event_id": "evt_generated_or_received"
}
```

HTTP-статусы:

```text
202 Accepted             — событие подтверждено брокером
422 Unprocessable Entity — ошибка валидации
503 Service Unavailable  — брокер недоступен, событие НЕ принято
```

Причина `202`: событие принято брокером, но ещё не обязательно записано в ClickHouse (см. 0.2).

### 6.3. POST /events/batch

Назначение: приём пачки событий.

Пример запроса:

```json
{
  "events": [
    {
      "event_type": "session_started",
      "event_time": "2026-07-16T12:30:00Z",
      "game_id": "arena_escape",
      "player_id": "player_123",
      "session_id": "session_456",
      "properties": {}
    },
    {
      "event_type": "level_started",
      "event_time": "2026-07-16T12:31:00Z",
      "game_id": "arena_escape",
      "player_id": "player_123",
      "session_id": "session_456",
      "properties": {
        "level_id": 1
      }
    }
  ]
}
```

Пример ответа (v2 — с деталями по отклонённым):

```json
{
  "status": "accepted",
  "accepted_count": 2,
  "rejected_count": 0,
  "errors": []
}
```

Пример ответа при частичной ошибке (правило MVP — отклоняем весь батч, но возвращаем причины):

```json
{
  "status": "rejected",
  "accepted_count": 0,
  "rejected_count": 2,
  "errors": [
    { "index": 1, "error": "event_time is more than 5 minutes in the future" }
  ]
}
```

Для MVP правило: если в пачке есть невалидное событие, отклоняется вся пачка — **но ответ обязан содержать индексы и причины**, иначе дебаг генератора превращается в боль. Частичное принятие — расширение.

### 6.4. GET /analytics/events/count

Назначение: получить общее количество сохранённых событий.

```json
{
  "total_events": 152340
}
```

Назначение: получить популярные типы событий.

### 6.6. GET /analytics/users/active

Назначение: количество активных игроков за период.

```text
GET /analytics/users/active?from=2026-07-16&to=2026-07-17
```

```json
{
  "active_players": 2450
}
```

### 6.7. GET /analytics/sessions/count

Назначение: количество уникальных игровых сессий.

```json
{
  "sessions_count": 4310
}
```

### 6.8. GET /analytics/levels/funnel

Назначение: простая воронка прохождения уровней.

```json
[
  { "level_id": 1, "started": 1000, "completed": 820 },
  { "level_id": 2, "started": 820, "completed": 610 }
]
```

Важно: этот endpoint зависит от `level_id` в `properties`. В v2 он ускорен `MATERIALIZED`-колонкой `level_id` (см. раздел 7).

Назначение (v2): системные метрики сервиса в формате Prometheus. Отдаётся каждым сервисом. Примеры счётчиков:

```text
events_received_total
events_written_total
processing_errors_total
consumer_lag
```

## 7. Схема таблицы ClickHouse

Основная таблица: `game_events`.

Пример SQL-схемы (v2):

```sql
CREATE TABLE IF NOT EXISTS game_events
(
    event_id String,
    event_type LowCardinality(String),
    event_time DateTime64(3, 'UTC'),
    received_at DateTime64(3, 'UTC'),

    game_id LowCardinality(String),
    player_id String,
    session_id String,

    platform LowCardinality(String),
    app_version LowCardinality(String),
    country LowCardinality(String),

    properties String,

    -- v2: materialized-колонки для частых запросов.
    -- Схема остаётся универсальной: значения вычисляются из properties,
    -- клиент по-прежнему шлёт только properties.
    level_id UInt32 MATERIALIZED JSONExtractUInt(properties, 'level_id')
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (game_id, event_type, event_time, player_id)
-- v2: retention. Для MVP можно закомментировать, но показать, что учтено.
TTL toDateTime(event_time) + INTERVAL 90 DAY;
```

Для перехода на дедупликацию (расширение) движок меняется на:

```sql
ENGINE = ReplacingMergeTree
ORDER BY (game_id, event_type, event_time, player_id, event_id)
```

...с обязательным `FINAL`/`argMax` в запросах (см. 0.4).

### Пояснение по полям

| Поле | Назначение |
| --- | --- |
| `event_id` | Уникальный идентификатор события (ULID) |
| `event_type` | Тип события |
| `event_time` | Время события на стороне клиента/источника (валидируется) |
| `received_at` | Время получения события backend-системой |
| `game_id` | Идентификатор игры или проекта |
| `player_id` | Идентификатор игрока |
| `session_id` | Идентификатор игровой сессии |
| `platform` | Платформа: android, ios, pc, web |
| `app_version` | Версия игры или клиента |
| `country` | Страна игрока |
| `properties` | JSON-строка с дополнительными параметрами события |
| `level_id` | v2: materialized из `properties.level_id`, ускоряет воронку |

### Почему properties хранится как строка

На этапе MVP это упрощает систему и делает её универсальной.

Преимущества:

- не нужно менять схему таблицы под каждый новый тип события;
- можно хранить события разных игр в одной общей модели;
- можно быстро подключать тестовые данные;
- специфичные параметры остаются доступными через JSON-функции ClickHouse;
- частые поля (например, `level_id`) при этом можно ускорить через `MATERIALIZED`, не ломая универсальность.

> Нативный тип `JSON` в ClickHouse для MVP не используется — местами он всё ещё нестабилен. `String` + `JSONExtract` (+ materialized-колонки) — прагматичный и надёжный выбор.

Пример извлечения поля из `properties` (без materialized-колонки):

```sql
SELECT
    JSONExtractInt(properties, 'level_id') AS level_id,
    count() AS events_count
FROM game_events
WHERE event_type = 'level_started'
GROUP BY level_id
ORDER BY level_id;
```

С materialized-колонкой запрос воронки не делает JSON-парсинг на каждой строке и работает по колонке `level_id` напрямую.

## 8. Логика очереди сообщений

Основной topic:

```text
game-events   (6–12 партиций)
```

Дополнительные topics после MVP:

```text
game-events-invalid
game-events-dead-letter
```

Базовая логика:

```text
1. Event API принимает событие и валидирует обязательные поля + event_time.
2. Event API сериализует событие в JSON.
3. Event API отправляет событие в topic game-events с acks=all.
4. Только после ack брокера Event API возвращает 202 (иначе 503).
5. Event Processor читает событие из game-events.
6. Event Processor валидирует и преобразует событие.
7. Event Processor накапливает батч и записывает его в ClickHouse.
8. Только после успешной записи Event Processor коммитит offset.
9. При ошибке — событие логируется (JSON) или отправляется в invalid/DLQ topic.
```

Ключ сообщения:

```text
message key = player_id
```

Это с большей вероятностью сохраняет порядок событий одного игрока внутри одной партиции (все события игрока идут в одну партицию).

Для MVP достаточно одного topic `game-events` (но с несколькими партициями) и логирования ошибок в stdout в структурированном виде.

## 9. Логика Event Processor

Алгоритм работы:

```text
1.  Подключиться к Redpanda/Kafka (enable.auto.commit = false).
2.  Подписаться на topic game-events (consumer group).
3.  Читать сообщения из очереди (poll).
4.  Десериализовать JSON.
5.  Провалидировать структуру события (Pydantic).
6.  Преобразовать событие в формат строки ClickHouse.
7.  Накопить batch.
8.  Если batch достиг размера N — записать в ClickHouse.
9.  Если прошло T секунд — записать неполный batch.
10. Только ПОСЛЕ успешной записи — commit offset.
11. При ошибке записи в ClickHouse — retry с экспоненциальным backoff,
    offset НЕ коммитить (событие переобработается).
12. При ошибке формата JSON/валидации — лог (JSON) + опционально invalid topic,
    offset коммитить (иначе застрянем на «ядовитом» сообщении).
```

Рекомендуемые параметры MVP:

```text
batch_size = 1000
flush_interval_seconds = 5
```

То есть запись в ClickHouse происходит, когда накопилось 1000 событий **или** прошло 5 секунд с последней записи.

### 9.1. Graceful shutdown (v2, критично)

При остановке контейнера (`SIGTERM` от Docker) processor обязан:

```text
1. Перестать читать новые сообщения.
2. Дописать текущий (недополненный) batch в ClickHouse.
3. Закоммитить offset.
4. Закрыть consumer и выйти.
```

Без этого при каждом редеплое или `--scale` теряется недописанный батч. Реализуется через обработчик сигнала и флаг `running`.

### 9.2. Согласование таймаутов (v2)

`max.poll.interval.ms` консьюмера должен быть заметно больше, чем максимально ожидаемое время обработки+записи одного poll-цикла. Иначе при затянувшейся записи в ClickHouse брокер исключит консьюмера из группы и начнётся ребаланс-шторм.

### 9.3. Обработка ошибок

Ошибка валидации события:

```text
записать ошибку в лог (JSON)
опционально отправить событие в game-events-invalid
offset закоммитить (сообщение не переобрабатывать бесконечно)
```

Ошибка записи в ClickHouse:

```text
retry с экспоненциальным backoff (с потолком, без busy-loop)
offset НЕ коммитить до успеха
```

Ошибка формата JSON:

```text
записать ошибку в лог (JSON)
опционально отправить исходное сообщение в invalid topic
offset закоммитить
```

Дубликат `event_id`:

```text
для MVP — не усложнять (система at-least-once, дубли ожидаемы)
после MVP — ReplacingMergeTree + FINAL/argMax или отдельная дедупликация
```

Для учебного проекта полноценная exactly-once не реализуется. Достаточно честно описать, что система обеспечивает at-least-once доставку с возможностью повторной обработки, а защита от дублей — расширение.

## 12. Этапы реализации MVP

### MVP-1. Инфраструктура

Цель: поднять базовые контейнеры.

- создать `docker-compose.yml` (с healthcheck'ами и `depends_on: service_healthy`);
- добавить ClickHouse;
- добавить Redpanda (топик `game-events` с несколькими партициями);
- добавить init SQL для таблицы `game_events`;
- проверить, что контейнеры запускаются и таблица создаётся автоматически.

### MVP-2. Event API

Цель: принять событие через HTTP.

- создать FastAPI-приложение;
- подключить общую Pydantic-модель из `shared/`;
- реализовать `GET /health`;
- реализовать `POST /events` (с валидацией `event_time`, статусами 202/422/503);
- реализовать `POST /events/batch` (с ошибками по индексам);
- добавить продюсер с `acks=all`.

Результат: событие отправляется в API и попадает в очередь; при недоступном брокере API отдаёт 503.

### MVP-3. Event Processor

Цель: переложить данные из очереди в ClickHouse.

- создать Kafka consumer (`enable.auto.commit = false`);
- читать сообщения из topic `game-events`;
- валидировать события общей моделью;
- накапливать batch (size/interval);
- записывать batch в ClickHouse;
- коммитить offset только после записи;
- реализовать graceful shutdown (SIGTERM);
- структурированное логирование.

Результат: событие проходит полный путь API → очередь → processor → ClickHouse.

### MVP-4. Генератор событий

Цель: создать тестовую нагрузку.

- генерировать игроков, сессии, разные типы событий (с ULID `event_id` на своей стороне);
- отправлять события в `Event API`;
- поддержать режим отправки батчами.

Результат: можно наполнить ClickHouse тысячами тестовых событий.

### MVP-5. Минимальные метрики

Цель: доказать, что сохранённые данные можно использовать.

- создать `Analytics API`;
- реализовать: количество событий, активных игроков, количество сессий, популярные типы, простую воронку.

Результат: backend не только хранит события, но и позволяет получать базовые агрегированные данные.

### MVP-6. Тесты

Цель: показать инженерный подход.

- валидное / невалидное событие;
- невалидный `event_time`;
- batch endpoint (в т.ч. ошибки по индексам);
- преобразование события для ClickHouse;
- обработка пустого `properties`;
- `GET /health`;
- **e2e через testcontainers** (реальные ClickHouse + Redpanda: POST → очередь → processor → строка в `game_events`);
- тест на повторную обработку (дубли).

Результат: ключевые части backend покрыты тестами, включая сквозной сценарий.

## 14. Риски и упрощения для учебного проекта

### Риск 1. Kafka может оказаться слишком тяжёлой
Упрощение: использовать Redpanda (совместима с Kafka API, проще в Docker Compose).

### Риск 2. Слишком сложная аналитика
Упрощение: ограничиться 4–5 базовыми метриками. Акцент — «backend pipeline работает», а не «построена BI-система».

### Риск 3. Слишком сложная схема событий
Упрощение: универсальные поля + `properties`. Частые поля ускоряем через `MATERIALIZED`, а не через отдельные колонки под каждый тип.

### Риск 4. Дубли и сложная семантика доставки
Упрощение: явно принять модель at-least-once, использовать `event_id` (ULID) и логирование. Exactly-once — расширение.

### Риск 5. Слишком много сервисов
Упрощение: двигаться по этапам (API → Queue → Processor → ClickHouse → Generator → Analytics → Grafana).

### Риск 6 (v2). Масштабирование не работает из-за одной партиции
Упрощение: сразу создать топик с 6–12 партициями. Иначе `--scale event-processor=N` не даст параллелизма.

### Риск 7 (v2). Потеря данных при рестарте processor
Упрощение: ручной commit offset после записи + graceful shutdown на SIGTERM.

## 17. Краткая итоговая формулировка проекта

Итоговый проект — это контейнеризированная backend-система для событийной игровой аналитики, которая принимает и валидирует универсальные игровые события через FastAPI, надёжно передаёт их через очередь сообщений Redpanda/Kafka (acks=all, партиционирование по `player_id`), обрабатывает отдельным Python-сервисом с at-least-once гарантией и ручным коммитом offset, сохраняет батчами в ClickHouse и предоставляет минимальные аналитические endpoints для проверки корректности хранения и обработки данных.

Главная ценность проекта:

```text
не конкретная аналитика одной игры,
а универсальный масштабируемый backend для сбора и хранения игровых событий.
```
