## 1. Зачем такие системы вообще нужны

Есть мобильная игра. Продуктовой команде надо знать: на каком уровне игроки бросают
игру, сколько людей доходит до покупки, растёт ли аудитория. Единственный способ это
узнать — чтобы игра сама сообщала о том, что в ней происходит.

Каждое действие игрока превращается в **событие**: «начал сессию», «прошёл уровень 4
за 128 секунд», «купил меч за 199 монет». Игра отправляет их на сервер.

Масштаб, из-за которого задача становится инженерной, а не студенческой:

- 100 000 игроков в день × ~50 событий на игрока = **5 млн событий в день**;
- события идут неравномерно — вечером в 10 раз больше, чем ночью;
- данных за год накапливаются миллиарды строк, и по ним надо считать отчёты за секунды.

Отсюда три требования, которые и определили всю архитектуру:

| Требование | Что из него следует |
| --- | --- |
| Принимать быстро и не терять при всплесках | Нужна **очередь** между приёмом и записью |
| Не терять события при падении базы | Нужен **ручной коммит offset** и ретраи |
| Считать агрегаты по миллиардам строк за секунды | Нужна **колоночная БД** (ClickHouse), а не Postgres |

Ключевая мысль проекта: это **не аналитика одной игры**, а универсальная труба, в
которую можно воткнуть любую игру. Поэтому в событии есть общие поля (`game_id`,
`player_id`, `event_type`) плюс свободное поле `properties` под специфику конкретной
игры. Схему БД не надо менять каждый раз, когда геймдизайнер придумал новое событие.

## 2. Docker: минимум, который надо понимать

### Проблема, которую решает Docker

Твоя система — это 5 разных программ: Python-сервисы, ClickHouse, Redpanda. У каждой
свои зависимости, свои версии, свои настройки. Поставить это всё руками на Windows —
день боли. Поставить это же на компьютер преподавателя — ещё день боли, и оно
не заработает, потому что у него другая версия Python.

Docker решает это так: программа упаковывается **вместе со своим окружением** в
изолированную коробку. Коробка запускается одинаково везде.

### Три понятия, которые надо различать

**Образ (image)** — рецепт, шаблон, «слепок диска». Неизменяемый. Твои образы видно
в Docker Desktop в колонке Image: `praktika-event-api`, `clickhouse`, `redpanda`.

**Контейнер (container)** — запущенный экземпляр образа. Живой процесс. Из одного
образа можно запустить хоть 3 контейнера — именно так работает
`docker compose up --scale event-processor=3`.

**Dockerfile** — инструкция, как собрать образ. Твой ([Dockerfile](../Dockerfile))
читается сверху вниз буквально:

```dockerfile
FROM python:3.12-slim      # взять готовый образ с Python 3.12
WORKDIR /app               # работать в папке /app внутри контейнера
COPY pyproject.toml README.md ./   # скопировать файлы внутрь образа
COPY src ./src
RUN pip install .          # установить проект как пакет
```

Заметь: один Dockerfile — один образ, но из него запускаются **четыре разных сервиса**
(event-api, event-processor, analytics-api, event-generator). Отличаются они только
командой запуска (`command:` в compose). Это нормальная практика для монорепозитория:
код общий, точки входа разные.

Важное следствие, на котором легко обжечься: **код запекается в образ на этапе сборки**.
Поменял `.py`-файл — контейнер об этом не узнает, пока не сделаешь `docker compose build`.

### Что означает `8010:8000`

На твоём скриншоте у `event-api-1` написано `8010:8000`. Это **проброс порта**:

```
localhost:8010  →  порт 8000 внутри контейнера
  (твой Windows)      (там слушает uvicorn)
```

Формат всегда `внешний:внутренний`. Внутри контейнера uvicorn слушает 8000 (см.
`command:` в compose), а наружу это выставлено как 8010, потому что 8000 на твоей
машине был занят другой программой. Внутренний порт при этом менять не пришлось.

У `analytics-api` — `8001:8001`, совпадают. У `clickhouse` — `8123:8123` (HTTP-интерфейс).

### Сеть между контейнерами

Контейнеры одного compose-проекта видят друг друга **по имени сервиса**. Поэтому в
настройках processor'а написано `PROCESSOR_CLICKHOUSE_HOST: clickhouse`, а не
`localhost`. Внутри контейнера `localhost` — это он сам, а не твой Windows.

Отсюда правило, которое путает всех новичков:

| Откуда обращаешься | Адрес ClickHouse |
| --- | --- |
| Из контейнера (processor, analytics-api) | `clickhouse:8123` |
| С Windows (браузер, curl, pytest) | `localhost:8123` |

### Volume — где живут данные

Контейнер эфемерен: удалил — всё внутри исчезло. Но база данных так работать не может.
Поэтому в compose есть:

```yaml
volumes:
  - clickhouse_data:/var/lib/clickhouse
```

`clickhouse_data` — именованный том, кусок диска, который живёт **отдельно от контейнера**.
Поэтому `docker compose down` не убивает твои 352 события, а `docker compose down -v`
(с флагом `-v`) — убивает. Будь осторожен с `-v`.

Второй volume — проброс init-скрипта:

```yaml
- ./docker/clickhouse/init:/docker-entrypoint-initdb.d:ro
```

ClickHouse при **первом** старте выполняет все `.sql` из этой папки. Так автоматически
создаётся таблица `game_events`. `:ro` = read-only, контейнер не может испортить твои
файлы. Важно: скрипты выполняются только при создании тома. Если поменял схему — нужен
`docker compose down -v`, иначе новый SQL не применится.

### Healthcheck и depends_on

```yaml
healthcheck:
  test: ["CMD-SHELL", "clickhouse-client --query 'SELECT 1'"]
  interval: 10s
  retries: 12
```

Docker раз в 10 секунд выполняет команду внутри контейнера. Отвечает — контейнер
`healthy`. Это не формальность: ClickHouse стартует несколько секунд, и без проверки
processor попытался бы подключиться к ещё не готовой базе и упал.

```yaml
depends_on:
  clickhouse:
    condition: service_healthy
```

«Не запускай processor, пока ClickHouse не ответит на `SELECT 1`». Без `condition`
Docker ждёт только *запуска* контейнера, а не его *готовности* — а это разные вещи.

### Команды, которые реально нужны

```bash
docker compose up -d          # поднять всё в фоне
docker compose ps             # что запущено (то же, что твой скриншот)
docker compose logs -f event-processor   # смотреть логи в реальном времени
docker compose restart event-processor   # перезапустить один сервис
docker compose build          # пересобрать образы после правки кода
docker compose down           # остановить и удалить контейнеры (данные живы)
docker compose down -v        # то же + удалить данные. ОСТОРОЖНО
docker exec praktika-clickhouse-1 clickhouse-client --query "SELECT 1"  # выполнить команду внутри
```

### Твой скриншот, построчно

- `praktika` — не контейнер, а **группа** (compose-проект). Разворачивается стрелочкой.
- `redpanda-init` — серый кружок, `0%`, статус завершён. Так и должно быть: это
  одноразовая задача, которая создаёт топик `game-events` с 6 партициями и умирает.
  У неё `restart: "no"` именно поэтому.
- `clickhouse-1` — 85% CPU. Норма сразу после рестарта: ClickHouse доперемалывает
  куски данных в фоне (merge). Через минуту-другую упадёт до единиц процентов.
- Три Python-сервиса едят по ~40 МБ и 0.3% CPU — они почти всё время просто ждут.

## 3. Разбор docker-compose.yml по строчкам

`docker-compose.yml` — это описание **всей системы целиком** одним файлом: какие
сервисы, как они связаны, какие настройки. Вместо пяти команд `docker run` с двадцатью
флагами каждая — один `docker compose up`.

Ключевые места твоего файла:

**Redpanda получает флаги ужатия под ноутбук:**
```yaml
--smp=1 --memory=512M --overprovisioned
```
Redpanda по умолчанию считает, что она на боевом сервере, и забирает все ядра и всю
память. `--overprovisioned` говорит «ты в контейнере на ноуте, веди себя скромно».

**Два адреса брокера — не опечатка:**
```yaml
--advertise-kafka-addr=PLAINTEXT://redpanda:9092,OUTSIDE://localhost:19092
```
Это ровно та же проблема «внутри контейнера / снаружи», что и с ClickHouse. Внутренние
сервисы подключаются по `redpanda:9092`, а pytest с твоего Windows — по
`localhost:19092`. Redpanda обязана сообщать клиенту адрес, по которому тот сможет к
ней вернуться, и адрес этот зависит от того, откуда клиент пришёл.

**Создание топика с 6 партициями** — сервис `redpanda-init`. Скрипт сначала проверяет,
не создан ли топик уже, и только потом создаёт. Это называется идемпотентность:
безопасно запускать повторно.

**`profiles: ["tools"]` у генератора** — он не поднимается вместе со всеми по
`docker compose up`. Это разовый инструмент, его дёргают руками:
`docker compose run --rm event-generator`. Флаг `--rm` удаляет контейнер после работы.

**Все настройки — через переменные окружения.** Ни одного адреса или пароля в коде.
Это принцип 12-factor app: один и тот же образ работает и локально, и на проде,
меняются только переменные.

## 4. Компоненты системы по одному

```
Игра / Event Generator
        ↓  HTTP POST
[ Event API ]            :8010 → приняли, проверили, отдали в очередь
        ↓  Kafka protocol, acks=all
[ Redpanda ]             топик game-events, 6 партиций — буфер
        ↓  consumer group, ручной commit
[ Event Processor ]      копит батч, пишет в БД, двигает закладку
        ↓  batch INSERT
[ ClickHouse ]           :8123 → хранит и агрегирует
        ↓  SELECT
[ Analytics API ]        :8001 → отдаёт метрики в JSON
```

### 4.1. Event API — [src/event_api/main.py](../src/event_api/main.py)

Входная дверь. Три эндпоинта: `/health`, `POST /events`, `POST /events/batch`.

Что делает с событием:
1. Валидирует структуру через Pydantic-модель `GameEventIn`.
2. Вызывает `normalize_event()`: проверяет `event_time`, генерирует `event_id` (ULID),
   если клиент не прислал, проставляет `received_at`.
3. Отправляет в Redpanda с `acks=all` и ключом `player_id`.
4. Возвращает `202 Accepted`.

**Чего он принципиально НЕ делает — не пишет в ClickHouse.** Это главное архитектурное
решение всего проекта. Если бы API писал в базу напрямую, то при вечернем всплеске
нагрузки медленная база затормозила бы приём, у игроков начались бы таймауты, и события
терялись бы прямо на входе. Очередь эту связь разрывает: API отвечает за миллисекунды
независимо от того, что происходит с базой.

Ты это **проверил экспериментально**: с полностью погашенным ClickHouse API принял
50 событий и вернул `202`. Ни одно не потерялось.

### 4.2. Redpanda — очередь сообщений

Kafka-совместимый брокер, но запускается одним контейнером без ZooKeeper. Работает как
журнал: сообщения дописываются в конец, лежат на диске, каждый потребитель помнит своё
место (offset).

Три вещи, которые она даёт:

**Буфер.** Пик нагрузки съедается очередью, а не базой.

**Развязка сервисов.** ClickHouse упал — события копятся в очереди. Поднялся —
разгребаются. Проверено на живой системе.

**Масштабирование.** Топик разрезан на **6 партиций** — 6 независимых дорожек. В одной
consumer group одну партицию читает ровно один потребитель, поэтому можно запустить до
6 processor'ов параллельно. Если бы партиция была одна, `--scale event-processor=3` дал
бы три процесса, из которых два просто стояли бы без дела.

**Ключ сообщения = `player_id`** ([producer.py:56](../src/event_api/producer.py:56)).
Партиция выбирается как хеш от ключа, значит все события одного игрока всегда попадают
в одну партицию и обрабатываются по порядку. Без этого `session_ended` мог бы записаться
раньше `session_started`.

### 4.3. Event Processor — [src/event_processor/main.py](../src/event_processor/main.py)

Самая содержательная часть проекта. Вечный цикл:

```python
while not stop_event.is_set():
    messages = await consumer.getmany(timeout_ms=..., max_records=batch_size)
    events = [parse_event_payload(m.value) for m in messages]  # битые — в лог, пропускаем
    await writer.insert_events(events)   # с ретраями и backoff
    await consumer.commit()              # ← закладка двигается ТОЛЬКО здесь
```

**Почему батчами.** ClickHouse ненавидит вставки по одной строке: каждая создаёт
отдельный кусок данных на диске, которые потом надо сливать. 1000 вставок по строке —
на порядки медленнее одной вставки на 1000 строк. Поэтому processor копит: до 500 событий
**или** до 2 секунд ожидания, что наступит раньше. Второе условие обязательно — иначе
при слабом трафике одно событие висело бы в памяти вечно.

**Почему commit в конце.** Offset — закладка «до какого места дочитано». Порядок
операций определяет, что случится при падении сервиса:

| Порядок | Что при падении посередине | Итог |
| --- | --- | --- |
| commit → запись | закладка сдвинута, данные не записаны | **потеря событий** |
| запись → commit *(наш вариант)* | данные записаны, закладка на месте | **дубли** |

Дубль можно потом схлопнуть. Потерянное событие не вернуть никогда. Поэтому осознанно
выбран второй вариант — это и есть гарантия **at-least-once**, «минимум один раз».

**Ретраи с backoff** — [clickhouse.py](../src/event_processor/clickhouse.py).
При ошибке записи: пауза `0.5s → 1s → 2s → 4s → ... → 30s (потолок)`, до 8 попыток,
перед каждой соединение пересоздаётся. Потолок нужен, чтобы задержка не росла
бесконечно, а сами паузы — чтобы не долбить лежащую базу в цикле. Если попытки
исчерпаны — исключение наверх, offset не коммитится, контейнер перезапускается
(`restart: unless-stopped`) и читает тот же батч заново.

**Graceful shutdown.** По `SIGTERM` от Docker выставляется флаг `stop_event`, цикл
доходит до конца итерации, дописывает батч, коммитит и закрывается. Без этого при каждом
перезапуске терялся бы недописанный батч. Флаг `stop_event` пробрасывается и в ретраи —
чтобы shutdown не ждал 30 секунд backoff'а.

**Битое сообщение → лог и пропуск, offset коммитится.** Логика обратная ошибке базы: если
в очередь попал невалидный JSON, ретраить бессмысленно, он невалиден навсегда. Не
пропустив его, processor встал бы на нём навечно — это называется «ядовитое сообщение»
(poison message).

### 4.5. Analytics API — [src/analytics_api/main.py](../src/analytics_api/main.py)

Витрина. Делает SELECT'ы к ClickHouse и отдаёт JSON. Не главный компонент — его задача

### 4.6. Event Generator — [src/event_generator/generator.py](../src/event_generator/generator.py)

Источник тестовой нагрузки. Собирает события из пула игроков (`player_00001`…),
платформ и стран по **каталогу событий преподавателя**: `session_start`,
`gameplay_start/win/lose/try_again/quit`, показы рекламы (`interstitial_ad_show`,
`rewarded_ad_*`), события сердец (`hearts_lost`, `hearts_recovered`, `hearts_add_ads`),
бустеры (`booster_buy`, `booster_spend`) и покупки (`purchase_start/success/failed`).
У каждого типа — свои осмысленные `properties` из методички препода (`level`, `hearts`,
`coins` для геймплея, `booster_type` и `booster_price` для бустеров, `product_id` и
`product_currency` для покупок).

Типы событий выбираются **взвешенно-случайно** (`random.choices` с весами): геймплей
частый, покупки редкие — как в живой игре. Точное распределение не гарантируется, это
случайная выборка.

Важная деталь: `event_id` генерируется **на стороне генератора**
([generator.py](../src/event_generator/generator.py)). Если бы его создавал API,
то повторная отправка того же HTTP-запроса дала бы два разных `event_id`, и
дедупликация стала бы невозможной в принципе.

**Честное ограничение, которое надо знать про свой же код.** Генератор нагружает
систему корректно, но правдоподобного поведения игроков не имитирует:

- `player_id` выбирается случайно на каждое событие, поэтому связной цепочки
  «этот игрок начал сессию → прошёл уровень → вышел» не получается;
- `event_time` — случайная точка в прошлом, так что события даже внутри одной сессии
  идут не по порядку.

Для проверки пропускной способности pipeline этого достаточно — а именно это и есть
цель проекта. Но воронка на таких данных показывает искусственные числа, и на защите
это лучше сказать самому, чем услышать в виде вопроса. Сделать генератор
сессионно-связным — понятное улучшение, если останется время.

## 5. ClickHouse: почему именно он

### Строки против колонок

Обычная БД (PostgreSQL, MySQL) хранит данные **строками** — все поля одной записи лежат
рядом:

```
[event_1: id, type, time, game, player, ...][event_2: id, type, time, ...]
```

Это отлично для «покажи мне заказ №5» — одно чтение. Но для запроса
`SELECT event_type, count() FROM game_events GROUP BY event_type` по 100 млн строк базе
придётся прочитать с диска **все 100 млн строк целиком**, включая ненужные колонки.

ClickHouse хранит **колонками** — все значения одного поля лежат вместе:

```
event_id:   [id1, id2, id3, ...]
event_type: [type1, type2, type3, ...]   ← прочитается только это
event_time: [t1, t2, t3, ...]
```

Тот же запрос читает одну колонку из одиннадцати. Плюс однотипные значения рядом
отлично жмутся. Отсюда разница в скорости на агрегатах — десятки и сотни раз.

Цена: ClickHouse плохо умеет `UPDATE`/`DELETE` отдельных строк и точечные запросы «дай
одну запись по id». Для событий это не нужно — они пишутся один раз и никогда не меняются
(append-only). Инструмент подобран под задачу.

### Схема таблицы, по строчкам

Файл [001_create_game_events.sql](../docker/clickhouse/init/001_create_game_events.sql):

```sql
event_type LowCardinality(String),
```
**`LowCardinality`** — у поля мало разных значений (6 типов событий, 4 платформы).
ClickHouse хранит словарь `{0: "level_started", 1: "session_ended", ...}` и вместо строк
пишет числа. Экономия памяти и ускорение группировок. Применять для полей с сотнями
уникальных значений, не больше. Поэтому `player_id` — обычный `String`: игроков миллионы.

```sql
PARTITION BY toYYYYMM(received_at)
```
**Партиционирование** — физическая нарезка данных по месяцам. Запрос за июль не трогает
файлы июня. Плюс удаление старых данных — это удаление партиции целиком, мгновенно.

Тонкость, которую стоит назвать на защите: партиционирование идёт по `received_at`
(время получения сервером), а **не** по `event_time` (время от клиента). `event_time`
приходит с телефона игрока, где могут быть кривые часы или намеренная подделка. Событие
с датой 2099 года создало бы мусорную партицию `209912`. `received_at` ставит сервер —
ему можно доверять.

```sql
ORDER BY (game_id, player_id, event_type, received_at, event_id)
```
**Ключ сортировки** — самое важное для скорости. Данные физически лежат на диске в этом
порядке, и ClickHouse строит по ним разреженный индекс. Запрос с фильтром по `game_id`
пропустит все чужие куски, не читая их. Порядок полей — от более общего к более частному.

```sql
level UInt32 MATERIALIZED JSONExtractUInt(properties, 'level')
```
**Materialized-колонка** — компромисс. `properties` хранится как JSON-строка ради
универсальности, но парсить JSON на каждой строке при каждом запросе дорого. Эта колонка
вычисляется **один раз при вставке** и дальше работает как обычная. Универсальность
схемы сохраняется — клиент по-прежнему шлёт только `properties`.

```sql
TTL toDateTime(received_at) + INTERVAL 180 DAY DELETE
```
**TTL** — автоудаление данных старше 180 дней. Без этого таблица растёт вечно.

### Почему properties — строка, а не JSON-тип

Потому что схема должна оставаться универсальной. Геймдизайнер придумал новое событие с
новыми полями — база не меняется вообще. Частые поля при этом ускоряются через
`MATERIALIZED`. Нативный тип `JSON` в ClickHouse на момент написания местами
нестабилен, поэтому взят надёжный вариант `String` + `JSONExtract`.

## 6. Путь одного события через всю систему

Полезно уметь рассказать это связно на защите.

**Шаг 1.** Игра шлёт `POST http://localhost:8010/events` с JSON события.

**Шаг 2.** FastAPI разбирает тело в модель `GameEventIn`
([shared/models.py:22](../src/shared/models.py:22)). Не тот тип, отсутствует
обязательное поле, `properties` больше 16 КБ → **422**, дальше событие не идёт.

**Шаг 3.** `normalize_event()` ([models.py:82](../src/shared/models.py:82)):
- `event_time` больше чем на 5 минут в будущем или старше 90 дней → **422**;
- нет `event_id` → генерируется ULID;
- проставляется `received_at = сейчас`.

**Шаг 4.** `send_and_wait()` шлёт событие в топик `game-events` с ключом `player_id`.
`acks=all` означает, что producer ждёт подтверждения о записи на диск. Брокер не ответил
→ **503**, и клиент знает, что событие НЕ принято.

**Шаг 5.** API возвращает **202 Accepted** — «принято брокером, в базе будет через
секунду-другую». Не `200`, потому что `200` означал бы «полностью обработано», а это
была бы ложь.

**Шаг 6.** Processor читает пачку сообщений из своих партиций, валидирует их той же
самой моделью (общий контракт в `shared/` — единственный источник правды, модель не
продублирована между сервисами).

**Шаг 7.** Копит батч до 500 событий или 2 секунд, конвертирует в строки, делает один
`INSERT` в ClickHouse. Ошибка → ретраи с backoff.

**Шаг 8.** Только после успешной записи — `consumer.commit()`.

**Шаг 9.** Данные доступны: `SELECT` напрямую или через Analytics API на `:8001`.

Задержка от `POST` до появления в базе — обычно 1–3 секунды. Это осознанный размен:
система **eventually consistent**, зато держит нагрузку и переживает падение базы.

## 7. Ключевые инженерные решения и их цена

Каждое решение — это размен. Умение назвать цену решения отличает понимание от заучивания.

| Решение | Что даёт | Чем платим |
| --- | --- | --- |
| Очередь между API и БД | API не зависит от скорости БД, переживает всплески | +1 сервис, данные появляются с задержкой |
| `202` только после ack брокера | Ответ не врёт клиенту | Латентность выше, чем при ответе сразу |
| At-least-once | Событий не теряем никогда | Возможны дубли, метрики приблизительные |
| Батчи по 500 | Запись в ClickHouse на порядки быстрее | Задержка до 2 секунд |
| 6 партиций | Масштабирование до 6 processor'ов | Порядок гарантирован только внутри игрока |
| `properties` строкой | Схема не меняется под новые события | Нужен `JSONExtract` при запросах |
| Партиции по `received_at` | Кривой клиент не сломает хранилище | Отчёт «по времени игрока» требует доп. фильтра |
| ULID вместо UUID4 | Сортируется по времени, лучше жмётся | Чуть менее привычен |

### Что честно не сделано (и это нормально)

- **Exactly-once** — не реализовано, вынесено в расширения. Требует транзакционности
  между Kafka и ClickHouse, что заметно сложнее.
- **Дедупликация** — дубли допускаются. Решение: `ReplacingMergeTree` + обязательный
  `FINAL`/`argMax` в запросах. Важно понимать: `ReplacingMergeTree` схлопывает дубли
  **отложенно, при слиянии кусков**. Само его наличие не гарантирует, что дублей нет
  прямо сейчас.
- **Dead-letter queue** — битые события пишутся в лог, отдельного топика для них нет.
- **Генератор не имитирует связное поведение игроков** (см. 4.6) — для нагрузки годится,
  для красивой воронки нет.
- **Известное узкое место:** `send_events()`
  ([producer.py:61](../src/event_api/producer.py:61)) отправляет батч по одному событию
  с ожиданием ack каждого. Корректно, но не быстро. Это первое, что надо чинить при
  замере throughput.

Признать ограничение и объяснить, почему оно допустимо, — сильная позиция на защите.
Утверждать, что всё идеально, — слабая: первый же вопрос это разрушит.

| --- | --- |

## 9. Вопросы на защите с ответами

**Почему не писать из API прямо в ClickHouse?**
Тогда скорость приёма событий упирается в скорость базы. При вечернем всплеске нагрузки
API начнёт таймаутиться, и события потеряются на входе. Очередь развязывает приём и
запись: API отвечает за миллисекунды, а база разгребает поток в своём темпе. Плюс при
падении базы события ждут в очереди — я это проверил, погасив ClickHouse и отправив 50
событий: все 50 дошли после подъёма базы.

**Почему 202, а не 200?**
`202 Accepted` = «принято в обработку, но ещё не завершено». Событие подтверждено
брокером, но в ClickHouse попадёт через секунду-две. `200` означал бы «полностью
обработано» и был бы враньём. Если брокер не подтвердил — возвращается `503`, и клиент
точно знает, что событие не принято.

**Что будет, если processor упадёт посередине батча?**
Ничего не потеряется. Offset коммитится только после успешной записи, поэтому после
перезапуска батч перечитается из Redpanda. Возможны дубли — это осознанная модель
at-least-once. Потеря необратима, дубль лечится дедупликацией.

**Почему ClickHouse, а не PostgreSQL?**
Задача — агрегаты по миллиардам append-only строк. Postgres хранит строками и вынужден
читать все данные целиком; ClickHouse хранит колонками и читает только нужные колонки,
плюс сильно жмёт однотипные значения. Взамен он плохо умеет точечные UPDATE — событиям
это не нужно, они неизменяемы.

**Зачем 6 партиций?**
Одну партицию в consumer group читает ровно один потребитель. С одной партицией
`--scale event-processor=3` дал бы три процесса, где работает один. Шесть партиций
позволяют масштабировать обработку до шести экземпляров.

**Зачем ключ `player_id`?**
Партиция выбирается по хешу ключа, поэтому все события одного игрока идут в одну
партицию и обрабатываются по порядку. Иначе `session_ended` мог бы обогнать
`session_started`.

**Гарантирует ли система отсутствие дублей?**
Нет, и это заявлено явно. Система at-least-once. Дедупликация — расширение через
`ReplacingMergeTree` с `FINAL` или `argMax`. Причём важно, что `ReplacingMergeTree`
схлопывает дубли отложенно, при слиянии кусков, так что запросы всё равно обязаны это
учитывать.

**Как система масштабируется?**
Горизонтально и независимо по слоям. API — добавить экземпляров за балансировщиком.
Обработка — `docker compose up --scale event-processor=3`, до числа партиций. Хранилище —
шардирование ClickHouse. Очередь развязывает слои, поэтому масштабировать можно то, что
стало узким местом, не трогая остальное.

**Почему properties — строка, а не отдельные колонки?**
Чтобы схема БД не менялась при каждом новом типе события и система оставалась
универсальной для разных игр. Частые поля ускоряются `MATERIALIZED`-колонками — как
`level` — без потери универсальности.

**Что не сделано?**
Exactly-once, дедупликация, dead-letter queue, Prometheus-метрики. Это осознанно вынесено
в расширения, чтобы MVP оставался завершённым и работающим.

## 10. Глоссарий

**Событие (event)** — факт того, что что-то произошло, с меткой времени. Неизменяем.

**Брокер сообщений** — промежуточное хранилище, принимающее сообщения от producer'ов и
отдающее consumer'ам. Redpanda, Kafka, RabbitMQ.

**Producer / Consumer** — тот, кто пишет в очередь / тот, кто читает.

**Топик (topic)** — именованный поток сообщений в брокере. У нас один: `game-events`.

**Партиция (partition)** — часть топика, независимая дорожка. Даёт параллелизм.

**Offset** — порядковый номер сообщения в партиции; «закладка» потребителя.

**Consumer group** — группа потребителей, делящих партиции между собой. У нас:
`game-events-clickhouse-writer`.

**Commit offset** — сохранить закладку в брокере.

**acks=all** — producer ждёт подтверждения записи от брокера, а не «отправил и забыл».

**At-least-once** — гарантия «минимум один раз»: не теряем, но возможны дубли.

**Идемпотентность** — свойство операции давать тот же результат при повторе.

**ULID** — 26-символьный идентификатор, сортируемый по времени создания.

**Backoff** — растущая пауза между повторными попытками.

**Poison message** — сообщение, которое всегда падает при обработке и блокирует очередь,
если его не пропустить.

**Graceful shutdown** — корректное завершение: доделать текущую работу, потом выйти.

**Колоночная СУБД** — хранит данные по колонкам, а не по строкам. Быстра на агрегатах.

**MergeTree** — основное семейство движков таблиц ClickHouse.

**Materialized-колонка** — колонка, вычисляемая один раз при вставке.

**TTL** — срок жизни данных, после которого они удаляются автоматически.

**Образ / Контейнер** — шаблон / запущенный экземпляр шаблона.

**Volume** — постоянное хранилище, переживающее удаление контейнера.

**Healthcheck** — периодическая проверка готовности контейнера.

**Eventually consistent** — данные появляются с задержкой, но обязательно появляются.
